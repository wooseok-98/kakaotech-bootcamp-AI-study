# 🎈 AI 학습 도우미 챗봇 만들기 (1) — 일단 대화부터 된다

AI 엔지니어 취업 포트폴리오로 **한국어 RAG 챗봇**을 만들기로 했다. 내가 부트캠프에서 정리한 학습 노트를 근거로 답해주는 "AI 학습 도우미"가 목표다.

한 번에 다 만들지 않고, 버전을 나눠 **단계적으로 발전**시키기로 했다.

| 버전 | 내용 |
| --- | --- |
| **v1** | 기본 대화 챗봇 (API) ← 이번 편 |
| v2 | 노트 RAG (검색해서 답하기) |
| v3 | LangChain으로 재구성 |
| v4 | LangGraph 에이전트 (소스 라우팅) |

이번 1편은 RAG도 프레임워크도 없이, **그냥 대화가 되는 챗봇**부터 만든다.

___

## 📌 왜 RAG부터 안 하고 기본 챗봇부터?

RAG가 이 프로젝트의 핵심이지만, 처음부터 RAG를 얹으면 "검색이 문제인지 LLM 호출이 문제인지" 구분이 안 된다. 그래서 **가장 단순한 동작(대화)부터 확실히 세우고**, 그 위에 RAG → LangChain → LangGraph를 한 겹씩 쌓기로 했다.

이렇게 하면 "같은 기능을 직접 짜보고(v2), 프레임워크로도 짜보고(v3), 에이전트로 확장(v4)"하는 **성장 과정**이 그대로 기록에 남는다.

___

## 📌 구조 — router → controller → core 3계층

FastAPI 서버를 한 파일에 다 때려넣지 않고 역할별로 나눴다.

```
브라우저 → [router] → [controller] → [core/llm.py] → Claude API
            요청 받기   흐름·기억 관리   외부 호출
```

| 계층 | 역할 |
| --- | --- |
| **router** | 요청을 받아 controller에 넘기는 얇은 창구 |
| **controller** | 대화 기억 관리 + 흐름 제어 |
| **core/llm.py** | 실제 Claude API 호출 |

특히 `core/llm.py`를 **"LLM을 교체하는 단 하나의 지점"**으로 설계했다. 나중에 모델을 바꾸거나(haiku ↔ opus), 파인튜닝한 모델로 갈아끼울 때 이 파일만 수정하면 되도록 한 것이다.

```python
# core/llm.py - 상위 코드는 이 함수만 호출, 어떤 모델인지 모른다
def chat(messages: list[dict]) -> str:
    response = client.messages.create(
        model=MODEL, max_tokens=1024,
        system=SYSTEM_PROMPT, messages=messages,
    )
    return response.content[0].text
```

## 📌 멀티턴의 비밀 — LLM은 기억이 없다

처음엔 "이전 대화를 LLM이 알아서 기억하겠지" 생각했는데 아니었다. **LLM API는 상태가 없다(stateless).** 매 호출이 완전히 독립적이다.

그럼 "내 이름 뭐였지?"에 어떻게 답할까? → **매번 이전 대화 전체를 같이 보내서** 기억을 흉내 낸다.

```
사용자 입력 → 이전 대화에 추가(user) → 전체 전송 → 답변 → 답변도 추가(assistant)
```

`messages` 리스트에 user / assistant를 계속 누적해서 통째로 보내는 게 멀티턴의 정체였다.

```python
messages = [
    {"role": "user",      "content": "내 이름은 우석이야"},
    {"role": "assistant", "content": "반가워요 우석님!"},
    {"role": "user",      "content": "내 이름 뭐였지?"},  # 이제 답할 수 있다
]
```

## 📌 대화를 어디 저장하지? — 메모리에서 SQLite로

처음엔 대화를 파이썬 딕셔너리에 담았다. 그런데 **서버를 끄거나 새로고침하면 다 날아갔다.** 딕셔너리는 메모리(RAM)에 사는데, RAM은 전원이 끊기면 사라지기 때문이다.

그래서 **SQLite**(파일 기반 DB)로 바꿨다. 대화를 디스크의 `messages` 테이블에 저장하니, 서버를 껐다 켜도 대화가 그대로 남았다.

| 저장 방식 | 위치 | 결과 |
| --- | --- | --- |
| 딕셔너리 | RAM(메모리) | 서버 끄면 소멸 |
| **SQLite** | 디스크(파일) | **영구 보존** |

여기에 `session_id`로 "누구의 대화인지"를 구분하고, 브라우저 `localStorage`에 session_id를 고정해서 **새로고침해도 지난 대화가 복원**되게 했다.

## 🎈 시행 착오

사실 나는 **웹 개발도 FastAPI도 처음**이고, **SQL/DB도 거의 안 써봤다.** 그래서 동작 자체보다 "이게 왜 이렇게 되는 거지?"에서 많이 막혔다.

### 📌 FastAPI: "내가 함수를 안 부르는데 어떻게 실행되지?"

가장 헷갈렸던 부분이다. `main.py`를 아무리 봐도 채팅 함수 `chat()`을 **직접 호출하는 코드가 없었다.** 그런데 동작은 한다.

알고 보니 일반 파이썬과 정반대였다.

```python
@router.post("/chat")   # 이건 "호출"이 아니라 "등록"이다
def chat(req): ...
```

- 일반 파이썬: 내가 `chat()`을 직접 부른다
- 웹 프레임워크: 나는 함수를 **등록만** 하고, 요청이 오면 **FastAPI가 대신 불러준다**

> "내가 라이브러리를 부르는 게 아니라, 라이브러리가 나를 부른다." 이걸 **제어의 역전(IoC)**이라고 부른다는 걸 알았다.

식당 메뉴판에 요리를 등록해두면(`@router.post`), 손님이 주문할 때(요청) 주방이 알아서 그 요리를 만드는(함수 실행) 것과 같았다. 이걸 이해하고 나니 3계층 구조도 비로소 눈에 들어왔다.

### 📌 SQL: "INSERT는 파이썬 문법이야, 아니야?"

DB 코드를 보다가 한참 헷갈린 게 이거였다.

```python
conn.execute("INSERT INTO messages (...) VALUES (?, ?, ?)", (...))
```

`INSERT INTO ...`가 파이썬 문법인 줄 알았는데 아니었다. **따옴표 안쪽은 SQL이라는 완전히 다른 언어**였다.

- 따옴표 바깥 = 파이썬
- 따옴표 안쪽 = SQL (DB에게 시키는 명령)

파이썬 입장에선 `"INSERT ..."`는 그냥 글자(문자열)일 뿐이고, 이걸 `conn.execute()`로 **DB 엔진에 전달**하면 DB가 그 SQL을 읽고 실행하는 구조였다. 한 코드 안에 **두 언어가 공존**한다는 걸 처음 알았다.

마지막으로 **`session_id`가 DB의 핵심 키**라는 것도 뒤늦게 이해했다. 세션 목록 UI를 안 만들 거라 session_id가 필요 없는 줄 알았는데, DB에 여러 사람 대화가 한 테이블에 쌓이니까 **"이 대화가 누구 것인지" 구분하는 열쇠**로 반드시 필요했다.

```sql
SELECT role, content FROM messages
WHERE session_id = ?   -- 이 세션 것만! (남의 대화 제외)
ORDER BY id
```

## 📌 배운 점 + 다음 편

- **FastAPI**: 함수는 등록하고, 호출은 프레임워크가 한다 (제어의 역전)
- **stateless**: LLM은 기억이 없어서 대화를 매번 다시 보낸다
- **DB**: 코드 안에 파이썬과 SQL 두 언어가 공존하고, session_id가 대화를 구분하는 키다
- 웹 개발이 처음이라 "동작"보다 "왜 이렇게 되는가"에서 더 배웠다

다음 편(v2)에서는 드디어 **RAG** — 내 학습 노트를 검색해서 그걸 근거로 답하게 만든다. 프레임워크 없이 직접 구현해서 원리부터 파볼 예정이다.
