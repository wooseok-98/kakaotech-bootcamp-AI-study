# 🎈 AI 학습 도우미 챗봇 만들기 (2) — 내 노트를 검색해서 답한다

[1편](https://velog.io/@dan9872/AI-%ED%95%99%EC%8A%B5-%EB%8F%84%EC%9A%B0%EB%AF%B8-%EC%B1%97%EB%B4%87-%EB%A7%8C%EB%93%A4%EA%B8%B0-1-%EC%9D%BC%EB%8B%A8-%EB%8C%80%ED%99%94%EB%B6%80%ED%84%B0-%EB%90%9C%EB%8B%A4)에서는 그냥 대화가 되는 챗봇을 만들었다. 그런데 문제가 하나 있었다. **Claude는 내가 정리한 노트를 모른다.** "내가 정리한 LSTM 게이트가 뭐였지?"라고 물으면, 내 노트가 아니라 자기가 학습한 일반 지식으로 답한다.

그래서 2편의 목표는 **RAG** — 내 학습 노트를 검색해서, 그걸 근거로 답하게 만드는 것이다. 이번엔 **프레임워크(LangChain) 없이 직접** 구현했다. 원리를 제대로 이해하고 싶었기 때문이다.

___

## 📌 RAG가 뭐고 왜 필요한가

**RAG(Retrieval-Augmented Generation)**는 이름 그대로다.

```
질문 → [관련 자료 검색] → 자료를 근거로 줌 → LLM이 답변
        ↑ 이 "검색"이 핵심
```

내 노트에서 질문과 관련된 조각을 찾아서, Claude에게 "이 내용을 근거로 답해"라고 같이 넘겨주는 것이다. 그럼 Claude가 일반 지식이 아니라 **내 노트 기반**으로 답하게 된다.

그럼 "관련 조각 찾기"를 어떻게 할까? 여기서 RAG의 부품들이 등장한다.

___

## 📌 RAG 파이프라인 — 4개의 부품

### 1️⃣ 임베딩 — 글을 "의미 좌표"로

관련 있는 노트를 어떻게 찾을까? 단순 키워드 매칭("LSTM"이란 단어 포함)은 약하다. "기억하는 신경망"이라고 물으면 단어가 달라서 못 찾는다.

그래서 글을 **의미를 담은 숫자 벡터**로 바꾼다. 이게 **임베딩**이다.

```
"LSTM은 기억하는 신경망"  →  [0.21, -0.03, ..., 0.15]  (숫자 768개)
"장기 기억 순환 신경망"    →  [0.19, -0.01, ..., 0.12]  (비슷한 숫자!)
"오늘 점심 뭐 먹지"       →  [-0.5, 0.7, ..., 0.9]     (전혀 다른 숫자)
```

핵심은 **의미가 비슷하면 벡터도 비슷해진다**는 것이다. 세상의 문장을 지도 위의 점으로 찍는다면, 비슷한 뜻은 가까운 위치에 모인다. 나는 한국어 임베딩 모델 `jhgan/ko-sroberta-multitask`(768차원)를 썼다.

> 실제로 테스트해보니 "LSTM은 기억하는 신경망"과 "장기 기억 순환 신경망"의 유사도가 **0.727**, 무관한 문장은 **-0.017**이 나왔다. 단어가 달라도 의미가 통하면 높게 나온다.

### 2️⃣ 청킹 — 문서를 의미 조각으로

노트 파일을 통째로 넣으면 관련 없는 내용이 섞인다. 그래서 **의미 단위로 잘라서** 각 조각을 임베딩한다.

노트는 `##` 헤더로 섹션이 나뉘어 있어서 **헤더 기준으로 잘랐다**. 68개 파일이 450조각이 됐다.

### 3️⃣ FAISS — 가까운 벡터를 빠르게 검색

조각이 수백 개니까, 질문마다 전부와 유사도를 계산하면 느리다. **FAISS**는 벡터를 저장해두고 "이 질문과 가장 가까운 top-k개 찾아줘"를 빠르게 해주는 도구다. 도서관 사서 같은 존재다.

> 여기서 헷갈린 개념 하나. **FAISS는 벡터(숫자)만 저장한다.** 검색하면 "42번이 가까워"라고 번호만 준다. 그래서 42번의 실제 원문은 `chunks.json`에 따로 저장해두고, 번호로 짝을 맞춰 꺼낸다.

### 4️⃣ 검색 + 생성

```
질문 → 임베딩 → FAISS로 top-k 검색 → 관련 조각 → Claude에게 근거로 전달 → 답변
```

`top_k`는 "가장 비슷한 상위 몇 개를 가져올지"다. 나는 4개로 했다. 한 조각만으론 부족할 수 있어서 여러 개를 모아 근거로 준다.

___

## 📌 grounding — 근거로만 답하게 묶기

검색한 조각을 그냥 주기만 하면 Claude가 자기 지식을 섞어 답할 수 있다. 그래서 **grounding**이 필요하다.

grounding은 답변을 **제공된 근거에 묶어두는 것**이다. 프롬프트로 이렇게 강제했다.

```python
RAG_SYSTEM = (
    "아래 제공된 [노트] 내용만 근거로 답해. "
    "노트에 없는 내용은 지어내지 말고 '노트에서 찾지 못했어요'라고 말해."
)
```

오픈북 시험에서 "이 교재로만 답하세요"라는 규칙과 같다. 실제로 "서울 날씨 어때?"를 물었더니 **"노트에서 찾지 못했어요"**라고 답했다. 할루시네이션 억제가 작동한 것이다.

## 📌 멀티소스 — 노트 + 위키피디아

내 노트만으론 부족한 주제가 있다. 그래서 **위키피디아**도 소스로 추가했다.

핵심 설계는 **"소스 하나 = 인덱스 하나"**다.

```
📒 노트   → notes_index  (450 조각)
📘 위키   → wiki_index   (313 조각, AI/ML 주제)

질문 → 두 인덱스 각각 검색 → 점수순 병합 → 상위 top-k
```

두 소스를 **같은 모델로 임베딩**했으니 점수를 직접 비교할 수 있다. 그래서 합쳐서 정렬하면 소스 상관없이 "가장 관련 높은 조각"이 나온다.

- **"트랜스포머가 뭐야?"** → 위키만 나왔다 (내 노트엔 트랜스포머가 거의 없으니까)
- **"RAG가 뭐야?"** → 노트만 나왔다 (위키엔 RAG 문서가 없으니까)
- **"LSTM 게이트?"** → 노트 + 위키가 섞여서 나왔다

노트에 없는 걸 위키가 채워주는 것. 이게 멀티소스의 존재 이유였다.

## 🎈 시행 착오

### 📌 위키 라이브러리를 3번 갈아엎었다

위키 문서를 받는 데 계속 실패했다.

1. **`wikipedia` 라이브러리** → `JSONDecodeError`. 알고 보니 User-Agent를 제대로 안 보내서, 짧은 시간에 여러 번 요청하면 위키가 차단 페이지를 돌려줬다.
2. **`wikipedia-api` 라이브러리** → `TypeError: unsupported operand type(s) for |`. 최신 버전이 `A | B` 타입 문법(Python 3.10+ 전용)을 쓰는데, 내 환경은 **Python 3.9**라 안 돌았다.
3. **결국 `requests`로 위키 API 직접 호출** → 성공. User-Agent를 직접 넣으니 차단도 안 당하고, 리다이렉트("딥 러닝" → "딥러닝")도 처리됐다.

> **교훈**: 라이브러리가 취약하면 API를 직접 호출하는 게 더 튼튼할 때가 많다. 남이 만든 추상화에 의존하다 막히면, 한 단계 밑으로 내려가는 것도 방법이다.

### 📌 답변이 잘려서 출처가 안 나왔다

노트 질문에 답은 잘 나오는데 **출처가 안 보였다.** 답변 끝을 보니 문장 중간에 뚝 끊겨 있었다. 원인은 `max_tokens`(답변 최대 길이) 제한이었다. 출처를 맨 끝에 쓰라고 했는데, 답변이 길어서 출처에 도달하기 전에 잘린 것이다. `max_tokens`를 늘려서 해결했다.

## 📌 배운 점 + 다음 편

- **RAG = 검색 + grounding.** 관련 자료를 찾아서(검색), 그걸로만 답하게(grounding) 묶는 것
- **임베딩**은 글을 의미 벡터로 바꿔 "의미로 검색"을 가능하게 한다
- **FAISS**는 벡터만 저장하니, 원문은 따로 짝지어 보관해야 한다
- **멀티소스**는 "소스 = 인덱스" 구조로 깔끔하게 확장된다
- 프레임워크 없이 밑바닥부터 만드니 각 부품이 왜 필요한지 확실히 이해됐다
