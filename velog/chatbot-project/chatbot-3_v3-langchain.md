# 🎈 AI 학습 도우미 챗봇 만들기 (3) — 같은 걸 LangChain으로 다시 만들기

[2편](여기에-2편-링크)에서는 RAG를 **프레임워크 없이 직접** 만들었다. 임베딩·FAISS·검색·grounding을 하나하나 코드로 조립했다.

3편의 목표는 조금 이상하다. **똑같은 RAG를 이번엔 LangChain으로 다시 만드는 것**이다. 기능은 완전히 같다. 왜 굳이 또 만들까?

___

## 📌 왜 같은 걸 또 만드나

이유는 두 가지다.

1. **직접 만들어봤기 때문에 프레임워크가 뭘 해주는지 정확히 안다.** v2에서 임베딩·검색·프롬프트를 손으로 다뤄봤으니, LangChain의 각 부품이 "아, 이게 그거구나" 하고 바로 매칭된다. 원리를 모르고 프레임워크부터 배우면 마법처럼 느껴지지만, 반대 순서면 명확하다.
2. **"프레임워크 없이도, 프레임워크로도 만들 수 있다"**는 걸 보여주기 위해서다. 실무에선 둘 다 필요하다.

___

## 📌 LangChain 부품 — v2에서 만든 것의 프레임워크 버전

놀랍게도, v2에서 직접 만든 것들이 LangChain엔 전부 부품으로 있었다.

| v2 (직접 구현) | v3 (LangChain 부품) |
| --- | --- |
| 임베딩 모델 래퍼 | `HuggingFaceEmbeddings` |
| `faiss.IndexFlatIP` + `chunks.json` | `FAISS.from_documents()` |
| 검색 함수 | `vectorstore.similarity_search()` |
| f-string 프롬프트 | `ChatPromptTemplate` |
| anthropic 클라이언트 | `ChatAnthropic` |
| controller의 수동 조립 | **LCEL 체인** |

특히 인상 깊었던 건 **FAISS 부분**이다. v2에선 "FAISS는 벡터만 저장하니 원문은 `chunks.json`에 따로 저장하고 번호로 짝맞춰야 한다"고 고생했는데, LangChain의 `FAISS.from_documents()`는 **벡터와 원문(Document)을 알아서 함께 관리**한다. 내가 손으로 하던 짝맞춤을 프레임워크가 대신 해주는 것이다.

```python
# v2: 임베딩 → FAISS 저장 → chunks.json 저장 (여러 줄)
# v3: 한 줄
store = FAISS.from_documents(docs, embeddings)
```

___

## 📌 LCEL — 부품을 파이프로 연결하는 체인

v3의 핵심은 **LCEL(LangChain Expression Language)**이다. v2에서 controller가 "검색 → 프롬프트 만들기 → LLM 호출 → 텍스트 추출"을 손으로 이었다면, LangChain은 이걸 **파이프(`|`)로 연결**한다.

```python
rag_chain = (
    RunnablePassthrough.assign(context=검색·포맷)   # 질문으로 검색 → context 채움
    | prompt                                        # 프롬프트에 끼움
    | llm                                           # Claude 호출
    | StrOutputParser()                             # 텍스트만 추출
)
```

리눅스의 `cat file | grep 검색어`처럼, **왼쪽 출력이 오른쪽 입력으로 흘러간다.** 데이터의 모양이 파이프를 타며 계속 바뀐다.

```
질문 dict → (검색) context 추가 → (프롬프트) 메시지 목록 → (LLM) AI응답 → (파서) 텍스트
```

이게 처음엔 낯설었다. "함수를 순서대로 부르면 되는데 왜 파이프로 잇지?" 싶었다. 그런데 이해하고 나니, **흐름 전체가 하나의 체인 객체**가 되어서 재사용·조합이 쉬워진다는 게 보였다. v2의 흐름이 여러 파일에 흩어져 있었다면, v3는 체인 한 줄에 담긴다.

___

## 📌 v2 vs v3 — 직접 구현 vs 프레임워크

같은 걸 두 방식으로 만들어보니 트레이드오프가 명확해졌다.

| | v2 (직접) | v3 (LangChain) |
| --- | --- | --- |
| 코드 양 | 많음 (부품마다 직접) | 적음 (부품 조합) |
| 원리 이해 | **높음** (다 짜봄) | 낮음 (블랙박스) |
| 유연성 | 높음 (다 내 손) | 프레임워크 방식 따라야 |
| 학습 곡선 | 원리 | 프레임워크 API |

**결과물은 완전히 동일했다.** 같은 질문에 같은 답이 나왔다. 그래서 든 생각은 — 프레임워크는 "덜 짜게" 해주지만, 원리를 모르면 막혔을 때 디버깅이 어렵다. **원리를 알고 프레임워크를 쓰는 게 가장 강하다**는 걸 몸으로 느꼈다.

## 🎈 시행 착오

### 📌 Python을 3.9에서 3.12로 갈아엎었다

2편에서 위키 라이브러리가 Python 3.9 때문에 안 돌았던 게 계속 걸렸다. LangChain을 비롯해 앞으로 쓸 라이브러리들이 점점 3.10+ 를 요구할 텐데, 3.9에 머물면 계속 발목 잡힐 것 같았다.

그래서 아예 **Python 3.12로 올렸다.** python.org 설치 프로그램으로 3.12를 깔고, 가상환경을 새로 만들고, 패키지를 다시 설치했다. torch를 다시 받느라 시간은 좀 걸렸지만, 인덱스·코드·API키는 파일이라 그대로 남아서 재설치만 하면 됐다.

> **교훈**: 버전 문제로 자꾸 막히면, 우회하기보다 근본(런타임 버전)을 올리는 게 나을 때가 있다. 특히 프로젝트 초반이면.

### 📌 위키 rate limit이 또 터졌다

인덱스를 다시 빌드하는데 위키 요청이 중간에 `JSONDecodeError`로 죽었다. 짧은 시간에 요청을 많이 보내서 위키가 차단한 것이다. 이번엔 두 가지로 방어했다.

1. 요청 사이에 `time.sleep(0.3)` — 속도를 늦춰 차단 회피
2. `resp.json()`을 `try/except`로 감싸기 — 응답이 JSON이 아니어도 크래시 대신 그 주제만 건너뛰기

한 번 겪은 문제라 이번엔 빠르게 잡았다.

## 📌 배운 점 + 다음 편

- **LangChain 부품 = v2에서 직접 만든 것의 프레임워크 버전.** 직접 만들어본 게 이해에 큰 도움이 됐다
- **LCEL 체인 = 부품을 파이프(`|`)로 연결한 파이프라인.** 데이터가 흐르며 모양이 바뀐다
- 같은 결과라도 **직접 구현은 원리를, 프레임워크는 생산성을** 준다. 둘 다 알아야 한다
- 구조를 잘 나눠둔 덕에 **`core/` 폴더만 교체**하면 됐다 (로더·DB·웹 골격은 그대로)
