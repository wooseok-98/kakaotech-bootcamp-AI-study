# 2-1. 데이터 타입 (FP32 · FP16 · BF16 · Mixed Precision · INT8 · INT4)

모델이 숫자(가중치·활성값)를 **몇 비트로 저장하는지** 정하는 형식 — 비트 수가 곧 메모리·속도·정밀도의 균형을 결정

> Quantization을 이해하기 위한 선행 개념 — 부동소수점은 소수점 위치를 **지수로 조절**해 같은 저장 공간으로 아주 작은 수와 큰 수를 함께 표현

---

## FP32 (32비트 부동소수점)

하나의 실수를 32비트로 표현하는 **IEEE 754 단정밀도** 형식 — 딥러닝의 오랜 기본 데이터 타입

### 비트 구조

| 영역 | 비트 | 역할 |
|---|---|---|
| 부호(Sign) | 1 | 양수(`0`)·음수(`1`) |
| 지수(Exponent) | 8 | 숫자의 크기 범위 (소수점 위치 이동) |
| 가수(Mantissa) | 23 | 숫자의 세부 값·정밀도 |

$$값 = (-1)^{부호} \times 1.가수 \times 2^{(지수 - 127)}$$

> **지수 bias 127**: 지수부(8비트, 0~255)는 양수만 저장하므로, 음수 지수까지 표현하려 중간값 127을 기준(=실제 지수 0)으로 사용 → 저장 시 `실제지수 + 127`, 읽을 때 `저장값 - 127`

| 항목 | 값 |
|---|---|
| 표현 범위 | 약 `1.18 × 10⁻³⁸` ~ `3.4 × 10³⁸` |
| 유효 자릿수 | 약 7자리 |
| 메모리 | 4바이트 (32비트) |

> 소수를 완벽히 저장하진 못함 — `-123.45` → 약 `-123.44999...`처럼 가장 가까운 값으로 반올림. 오차는 무작위가 아니라 규칙적이지만, 수십억 번 누적되면 영향 가능 → FP32는 범위·정밀도가 넓어 학습 안정성이 좋음

### IEEE 754 특수 값

| 값 | 의미 |
|---|---|
| `+Inf` / `-Inf` | 표현 범위를 넘은 양/음의 무한대 |
| `NaN` (Not a Number) | 숫자로 정의 불가한 계산 결과 |

> 학습 중 손실이 `NaN`이면 수치 불안정 신호 — 학습률 낮추기·그래디언트 클리핑·입력 점검

### 코드 (PyTorch 기본 = FP32)

```python
import torch, torch.nn as nn

model = nn.Linear(768, 256)
print(model.weight.dtype)          # torch.float32 (기본)

param_count = sum(p.numel() for p in model.parameters())   # 768*256 + 256 = 196,864
print(param_count * 4 / 1024)      # 769.0 KiB (FP32: 파라미터당 4바이트)
```

## FP16 (16비트 부동소수점)

16비트로 실수를 표현하는 **IEEE 754 반정밀도** 형식 — FP32와 같은 구조지만 칸 수가 절반

### 비트 구조

| 영역 | 비트 | FP32 대비 |
|---|---|---|
| 부호 | 1 | 동일 |
| 지수 | 5 | 8 → 5 (범위 축소) |
| 가수 | 10 | 23 → 10 (정밀도 축소) |

$$값 = (-1)^{부호} \times 1.가수 \times 2^{(지수 - 15)}$$

> **지수 bias 15** (지수부 5비트, 0~31 → 기준 15)

| 항목 | 값 |
|---|---|
| 최대 유한값 | `65,504` |
| 유효 자릿수 | 약 3.3자리 |
| 메모리 | 2바이트 (FP32의 절반) |

### 사용 이유

- **메모리 절반**: 7B 모델 기준 FP32 약 28GB → FP16 약 14GB (기울기·옵티마이저 상태까지 합치면 GPU 탑재 가능 여부를 가름)
- **속도**: NVIDIA **Tensor Core**(행렬 연산 특화 하드웨어)로 FP16 연산 가속 — A100 기준 FP32 19.5 TFLOPS vs FP16 312 TFLOPS

> 단, 이는 **이론 성능** — 실제 속도는 모델 구조·배치·데이터 로딩·커널 구현에 좌우. "FP16이면 항상 N배 빠름"은 아님

### 코드 (`.half()`로 변환)

```python
model = nn.Linear(768, 256).half()     # FP16으로 변환
x = torch.randn(1, 768).half()          # 입력도 같은 dtype으로 맞춤
print(model.weight.dtype)               # torch.float16
print(sum(p.numel() for p in model.parameters()) * 2 / 1024)   # 384.5 KiB (파라미터당 2바이트)
```

> 데이터 타입만 바뀌고 파라미터 **개수는 불변** — 파라미터당 저장 크기만 절반

> **한계**: 지수 5비트라 범위가 좁아 큰 값은 오버플로, 작은 기울기는 언더플로 위험 → FP16 단독 학습은 불안정. 실무는 FP16+FP32 혼합 사용 (아래 Mixed Precision Training)

## BF16 (Brain Float 16)

Google Brain이 설계한 16비트 형식 — **지수부는 FP32와 동일(8비트)**, 가수부만 7비트로 축소

### 비트 구조

| 영역 | 비트 | 특징 |
|---|---|---|
| 부호 | 1 | |
| 지수 | 8 | **FP32와 동일** → 넓은 수치 범위 |
| 가수 | 7 | FP16(10)보다 낮은 정밀도 |

> 핵심: **FP32의 넓은 범위 + FP16의 메모리 절감**을 절충 — `-123.45` 저장 시 FP32 가수 23비트 중 상위 7비트만 사용 (지수부는 FP32와 그대로 동일)

> 비유: 넓은 지도를 작은 종이에 그린 것 — 담기는 범위는 넓지만 골목·건물 같은 세부는 거침

### FP16 vs BF16의 트레이드오프

딥러닝 학습에선 세밀함보다 **큰 값·작은 값을 안정적으로 표현하는 범위**가 더 중요한 경우가 많음 → FP16보다 BF16을 선호

### 코드 (`.bfloat16()`로 변환)

```python
model = nn.Linear(768, 256).bfloat16()   # BF16으로 변환
x = torch.randn(1, 768).bfloat16()
print(model.weight.dtype)                # torch.bfloat16
print(sum(p.numel() for p in model.parameters()) * 2 / 1024)   # 384.5 KiB (FP16과 동일, 2바이트)
```

> **하드웨어 지원 필요**: NVIDIA는 A100부터 BF16 Tensor Core 지원 (H100/H200·Blackwell, TPU도 핵심 형식). V100·RTX20 등 구세대는 네이티브 미지원 → `torch.cuda.is_bf16_supported()`로 확인

## FP32 vs FP16 vs BF16 비교

| 항목 | FP32 | FP16 | BF16 |
|---|---|---|---|
| 전체 비트 | 32 | 16 | 16 |
| 지수 / 가수 | 8 / 23 | 5 / 10 | 8 / 7 |
| 수치 범위 | 가장 넓음 | 좁음 (최대 65,504) | FP32와 거의 동일 |
| 유효 자릿수 | 약 7 | 약 3.3 | 약 2.4 |
| 오버플로 위험 | 낮음 | 높음 | 낮음 |
| 메모리 | 기준 (4B) | 절반 (2B) | 절반 (2B) |
| 학습 안정성 | 가장 안정 | 낮을 수 있음 | 높음 |
| 주 용도 | 기본 학습·마스터 가중치 | Mixed Precision·추론 경량화 | 대규모 모델 학습 |

> 같은 16비트라도 **비트 배분**이 다름 — FP16은 정밀도(가수↑), BF16은 범위(지수↑)에 투자

## Mixed Precision Training

무거운 연산은 **FP16/BF16 저정밀도**로 빠르게 처리하고, 가중치 누적·업데이트는 **FP32**로 유지해 속도·메모리와 수치 안정성을 함께 확보하는 학습 기법

> 연산은 빠른 16비트로, 누적은 안전한 32비트로 **분업** — 단계마다 가장 적절한 dtype을 골라 씀

### 학습 흐름 (매 스텝 반복)

| 단계 | dtype | 설명 |
|---|---|---|
| 1. 순전파 | FP16/BF16 | 저정밀도 복사본으로 예측 계산 |
| 2. 손실 계산 | FP16/BF16 | 민감한 연산은 자동으로 FP32 처리될 수 있음 |
| 3. Loss Scaling | FP16 (BF16 불필요) | 손실에 스케일 팩터를 곱해 기울기 언더플로 방지 |
| 4. 역전파 | FP16/BF16 | 스케일된 손실로 저정밀도 기울기 계산 |
| 5. 마스터 가중치 업데이트 | FP32 | unscale 후 FP32 가중치·옵티마이저 상태에 반영 |
| 6. 저정밀도 복사 | FP32 → FP16/BF16 | 갱신된 FP32를 다시 저정밀도로 복사, 다음 순전파에 사용 |

> `학습률 × 기울기`처럼 작은 값 누적은 FP32 마스터 가중치에 모으고, 무거운 행렬 연산은 저정밀도로 빠르게 처리

### Loss Scaling

FP16의 좁은 범위 때문에 작은 기울기가 `0`으로 사라지는(언더플로) 문제 방지 — **손실을 잠시 키워 역전파 후 원래 크기로 복원**

```
기울기 0.00001 (FP16 최소 정규화 수 ~6.1e-5보다 작아 소실 위험)
→ 손실 × 1024 → 역전파 → 기울기 0.01024 (표현 가능)
→ 업데이트 직전 unscale: 0.01024 ÷ 1024 = 0.00001 → FP32에 반영
```

> PyTorch `GradScaler`가 **동적 스케일링** 자동 처리 — 오버플로 감지 시 스케일 축소, 안정적이면 확대. 사용자가 팩터를 직접 튜닝할 필요 없음

### 코드 (autocast + GradScaler)

- **`autocast`**: 연산마다 적절한 dtype 자동 선택 (행렬곱은 FP16, softmax·정규화 등 민감 연산은 FP32) — 모델 가중치를 영구 변환하는 게 아님
- **`GradScaler`**: FP16 Loss Scaling 자동화

```python
from torch.amp import autocast, GradScaler

model = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.float32, device_map="cuda")
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-5)
scaler = GradScaler("cuda")

optimizer.zero_grad()
with autocast("cuda", dtype=torch.float16):   # 순전파·손실만 저정밀도
    loss = model(**batch).loss
scaler.scale(loss).backward()                  # 스케일된 역전파
scaler.step(optimizer)                          # unscale 후 업데이트 (Inf/NaN이면 스킵)
scaler.update()                                 # 다음 스텝 스케일 팩터 조정
# master weight dtype은 계속 torch.float32 유지
```

```python
# BF16: 지수 범위가 넓어 GradScaler 없이 진행
with autocast("cuda", dtype=torch.bfloat16):
    loss = model(**batch).loss
loss.backward()
optimizer.step()
```

> BF16 Mixed Precision은 FP32와 같은 지수 범위라 **Loss Scaling 불필요**

## INT8 (8비트 정수)

하나의 값을 8비트 **정수**로 저장 — 부호 있는 형식은 `-128 ~ 127`, 총 256개 정수 표현

> 부동소수점이 아닌 정수 — 수많은 FP32 실수를 그대로 담지 않고 **가장 가까운 정수 256칸 중 하나로 매핑**. 비유: FP32가 mm 자(약 40억 눈금)라면 INT8은 cm 자(256 눈금)

| 종류 | 범위 | 용도 |
|---|---|---|
| signed | `-128 ~ 127` | 가중치 (양·음 모두) — 양자화에 주로 사용 |
| unsigned | `0 ~ 255` | ReLU 출력처럼 항상 0 이상 |

### 양자화 원리 (scale 매핑)

`scale` = 정수 한 칸이 대응하는 FP32 간격 → 값을 `scale`로 나눠 반올림·clip

```
FP32 분포 -1.0~1.0 가정 → scale = 1.0 / 127 ≈ 0.007874
0.372 ÷ 0.007874 ≈ 47.244 → round → 47 → INT8 저장
복원: 47 × 0.007874 ≈ 0.3701   (원본 0.372, 양자화 오차 ≈ 0.0019)
```

> 값을 완벽 보존이 아니라 **근사 저장**하고 그 대가로 메모리 절감 — 가중치는 대부분 0 근처에 몰려 있어 256칸으로도 정보가 어느 정도 보존됨. 단, 수학추론·코드생성·긴 문맥은 품질 저하가 잘 나타나므로 반드시 평가셋 비교 필요

### 코드

```python
import torch

torch.iinfo(torch.int8).min, torch.iinfo(torch.int8).max   # (-128, 127)

x = torch.tensor([-1.0, -0.5, 0.0, 0.372, 0.5, 1.0])
scale = 1.0 / 127
q = torch.clamp(torch.round(x / scale), -127, 127).to(torch.int8)
# tensor([-127, -64, 0, 47, 64, 127], dtype=torch.int8)

param_count = 196864
print(param_count * 1 / 1024)   # 192.25 KiB — FP32(769) 대비 1/4, FP16(384.5) 대비 1/2
```

> 7B 모델 가중치: FP32 28GB → FP16 14GB → **INT8 7GB**

## INT4 (4비트 정수)

하나의 값을 4비트 정수로 저장 — 부호 있는 형식은 `-8 ~ 7`, 총 **16개** 정수만 표현

> INT8과 같은 정수 양자화지만 비트가 절반 → 표현 값이 256개에서 16개로 **1/16** 축소, 칸 간격이 훨씬 큼

### 양자화 원리 (INT8과 동일, 칸만 16개)

```
scale = 1.0 / 7 ≈ 0.142857   (INT8은 1.0/127 ≈ 0.007874)
0.372 ÷ 0.142857 ≈ 2.604 → round → 3 → INT4 저장
복원: 3 × 0.142857 ≈ 0.4286   (오차 ≈ 0.0566 — INT8의 약 30배)
```

> 오차는 커지지만 메모리는 값당 0.5바이트 (FP32의 **1/8**, INT8의 1/2)

### 메모리 절감 (가중치 기준)

| 모델 | FP32 | FP16 | INT8 | INT4 |
|---|---|---|---|---|
| 7B | 28GB | 14GB | 7GB | **3.5GB** |
| 70B | 280GB | 140GB | 70GB | **35GB** |

> 단순 메모리 절감이 아니라 **사용 가능한 모델 크기 자체를 바꾸는** 최적화 — 다중 GPU 필요하던 70B도 단일 고용량 GPU 검토 수준으로 내려옴. 단, 실제 추론 메모리는 KV Cache·활성화·비양자화 레이어까지 더해지므로 "INT4 70B = 35GB니 40GB GPU에 무조건 올라감"은 단정 금물

### 코드 (PyTorch에 int4 dtype 없음 → NumPy 시연)

```python
import numpy as np

np.arange(-8, 8)   # [-8 ... 7] — INT4가 쓸 수 있는 16개 칸

x = np.array([-1.0, -0.5, 0.0, 0.372, 0.5, 1.0], dtype=np.float32)
scale = np.max(np.abs(x)) / 7
q = np.round(x / scale).clip(-8, 7).astype(np.int8)   # [-7 -3 0 3 3 7]
dq = q * scale                                          # 복원 (오차 확인)

param_count = 768 * 256 + 256
print(param_count * 0.5 / 1024)   # 96.125 KiB — FP32(769)의 1/8, INT8(192.25)의 1/2
```

> INT4는 QLoRA 학습의 기반 — 큰 모델을 INT4로 고정하고 작은 LoRA 어댑터만 학습 ([[6-1_peft]] 참고)

## 데이터 타입 종합 비교

| 항목 | FP32 | FP16 | BF16 | INT8 | INT4 |
|---|---|---|---|---|---|
| 표현 방식 | 부동소수점 | 부동소수점 | 부동소수점 | 정수 | 정수 |
| 비트 / 값당 메모리 | 32 / 4B | 16 / 2B | 16 / 2B | 8 / 1B | 4 / 0.5B |
| 7B 가중치 | 28GB | 14GB | 14GB | 7GB | 3.5GB |
| 정밀도 | 가장 높음 | 중간 | 낮음(범위↑) | 256칸 근사 | 16칸 근사 |
| 주 용도 | 기본 학습·마스터 가중치 | Mixed Precision·추론 | 대규모 학습 | 추론 경량화·서빙 | 대형 모델 절감·QLoRA |
