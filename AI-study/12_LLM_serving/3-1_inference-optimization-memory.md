# 3-1. 추론 최적화 ① 메모리·스케줄링 (KV Cache · Continuous Batching · PagedAttention · Prefix Caching)

LLM 서빙에서 **GPU 메모리를 아끼고 요청을 촘촘히 채워** 같은 하드웨어로 더 많은 요청을 처리하는 4가지 핵심 기법 — 모두 vLLM 내부에서 동작

> 1-1에서 "뒤 페이지에서 상세히" 예고한 그 내용 — KV Cache(재사용)·Continuous Batching(스케줄링)·PagedAttention(메모리 관리)·Prefix Caching(요청 간 재사용)

---

## KV Cache

LLM 추론 중 이전 토큰들의 **Key·Value 벡터를 GPU 메모리에 저장**해 두고, 다음 토큰 생성 시 재사용해 중복 Attention 연산을 줄이는 캐시 구조

> **연산을 메모리로 맞바꾸는 것** — 전체 시퀀스를 매번 다시 계산하던 것을, 새 토큰 하나만 계산하고 나머지는 저장소에서 꺼내 씀. 대부분 프레임워크에서 기본 활성화

### 동작 원리 — Prefill에서 생성, Decode에서 재사용

| 단계 | KV Cache 동작 |
|---|---|
| **Prefill** | 입력 프롬프트 전체를 처리하며 각 토큰의 Key·Value를 계산해 GPU 메모리에 저장 |
| **Decode** | 새 토큰의 Key·Value만 계산, 이전 토큰들은 캐시에서 읽어 사용 |

> 새 토큰마다 앞 토큰들의 Key·Value가 필요한데 이 값은 **한 번 계산하면 바뀌지 않음** → 저장해 두고 재사용. 웹 비유: 무거운 연산 결과를 HTTP 캐시·Redis·메모이제이션으로 재사용하는 것과 결이 같음

### 서빙 관점 — 동시 처리량의 병목

- KV Cache는 **요청마다 따로 생성** — 요청 1건이 1GB면 동시 10건은 약 10GB
- 동시 요청 수·문맥 길이가 늘수록 VRAM 사용량도 같은 비율로 증가
- **동시 처리 가능한 요청 수를 제한하는 주요 메모리 요인** → 속도·메모리·동시 처리량을 함께 결정하는 핵심 요소

### 사용 방법 — vLLM이 자동 관리

vLLM에서 KV Cache는 끄고 켜는 대상이 아니라, **점유율을 관찰하고 공간을 조절**하는 대상

| 항목 | 방법 |
|---|---|
| 점유율 확인 | `/metrics`의 `vllm:gpu_cache_usage_perc` (0~1, `1`=100%에 가까울수록 처리 여력↓) |
| 공간 조절 | 서버 실행 시 `--gpu-memory-utilization` (값↑ → KV Cache 공간↑) |
| 점유율 변화 요인 | 동시 요청 수(`--max-num-seqs`)·문맥 길이 |

```python
# /metrics에서 처리 중 요청 수와 KV Cache 점유율 추출
def read_metrics():
    text = requests.get("http://localhost:8000/metrics").text
    running, cache = 0.0, 0.0
    for line in text.splitlines():
        if line.startswith("vllm:num_requests_running"):   # GPU에서 처리 중인 요청 수
            running = float(line.split()[-1])
        if line.startswith("vllm:gpu_cache_usage_perc"):    # KV Cache 점유율 (0~1)
            cache = float(line.split()[-1])
    return running, cache
```

> 점유율은 **누적이 아니라 측정 시점의 값** — 요청 처리 중엔 `0.0005`처럼 올라가고, 요청 완료 후엔 블록이 해제돼 `0.0`으로 돌아감

## Continuous Batching

매 Decode 스텝마다 **완료된 요청을 배치에서 빼고, 대기 중인 새 요청을 즉시 채워** 배치 구성을 계속 갱신하는 스케줄링 기법

> Static Batching은 배치 전체가 끝날 때까지 빈 슬롯을 방치 — Continuous Batching은 요청이 끝나는 즉시 슬롯을 다시 채움. 웹 비유: **자리가 비는 즉시 다음 손님을 앉히는 식당**

### Static vs Continuous

요청마다 출력 길이가 다르기 때문에(짧은 답변 ~ 수백 토큰), 배치를 고정하면 먼저 끝난 요청의 자리가 비어 남음

```
[Static Batching]                      [Continuous Batching]
Step2  [A완료][B][C][D]                Step2  [A완료][B][C][D]
Step3  [빈슬롯][B][C][D]  ← 대기        Step3  [E새요청][B][C][D]  ← 즉시 채움
→ 배치 전체가 끝나야 새 요청 투입        → A가 끝난 자리에 대기 요청 E를 바로 투입
```

> 핵심: 배치는 **고정된 묶음이 아니라 Decode 스텝마다 갱신되는 실행 단위** — 짧은 요청이 먼저 끝나도 자리를 비워 두지 않음

### 사용 이유·효과

- 요청 길이가 제각각인 실제 트래픽에서 **GPU 슬롯이 비는 시간↓** → 같은 GPU로 처리 요청 수↑, 대기 큐↓, 응답 대기 시간↓
- 효과는 **짧은 요청과 긴 요청이 섞일수록 커짐** (모든 요청 길이가 비슷하면 Static과 차이 적음)

### 사용 방법 — 기본 활성화

- vLLM·TGI 등 서빙 엔진에서 **별도 설정 없이 항상 동작** — 직접 켜고 끄는 기능 아님
- 조정 대상은 `--max-num-seqs` (한 배치에 담을 요청 수 상한 = 채울 슬롯 개수) — 키우면 처리량↑, 그만큼 KV Cache 메모리도↑

> **Prefill-Decode interference**: 새 요청이 추가되면 먼저 Prefill을 거쳐야 함. 엔진은 기존 요청 Decode 사이에 새 요청 Prefill을 끼워 넣는데, Prefill은 연산량이 커 기존 요청 지연시간이 잠깐 늘 수 있음

## PagedAttention

KV Cache를 **고정 크기 블록으로 나누어 비연속 GPU 메모리에 저장**하고, Attention 계산 시 블록 테이블로 필요한 블록을 찾아 참조하는 KV Cache 관리 방식

> **OS 가상 메모리의 페이징**과 같은 발상 — 물리적으로 흩어진 블록을 요청 입장에선 하나의 연속 KV Cache처럼 보이게 함. vLLM의 핵심 KV Cache 관리 방식

### 왜 필요한가 — 연속 할당의 낭비

- 기존 방식: 요청 하나의 KV Cache를 **하나로 이어진 큰 메모리**에 할당
- 응답 길이를 미리 몰라 넉넉히 예약 → 실제 안 쓰는 빈 공간 발생 + 해제된 공간이 작은 조각으로 흩어짐
- VRAM 전체는 남아 보여도 실제 서빙 가용 공간↓, 요청 몰리면 OOM

### 동작 원리 — 블록 단위 동적 할당

| 순서 | 단계 | 설명 |
|---|---|---|
| 1 | 블록 분할 | KV Cache 영역을 고정 크기 블록으로 분할 (블록 1개 = 예: 16토큰분 Key·Value) |
| 2 | 블록 테이블 생성 | 각 요청이 어떤 블록을 쓰는지 기록 |
| 3 | 동적 할당 | 토큰이 늘 때마다 필요한 만큼 블록 추가 (물리적으로 안 붙어 있어도 됨) |
| 4 | Attention 계산 | 블록 테이블 참고해 필요한 Key·Value 블록을 찾아 사용 |
| 5 | 블록 해제 | 요청 종료 시 블록 반환 → 다른 요청이 재사용 |

> 최악의 응답 길이를 가정해 큰 메모리를 예약할 필요가 줄어 **같은 GPU 메모리를 더 촘촘히 사용** → 동시 요청↑, OOM 가능성↓. 블록 탐색 비용은 vLLM의 최적화된 CUDA 커널이 흡수

### 사용 방법 — vLLM 기본 활성화

- vLLM의 KV Cache 관리 방식 그 자체 → 서버를 띄우는 순간 자동 적용, 클라이언트 코드는 그대로
- 조정 여지: `--block-size` (블록 1개가 담을 토큰 수, **기본값 16**)

> 블록 크기 트레이드오프: 키우면 관리 오버헤드↓·내부 단편화↑, 줄이면 단편화↓·관리할 블록 수↑. **기본값 16은 메모리 낭비와 관리 비용의 균형점** — 대부분 그대로 사용

## Prefix Caching

여러 요청이 공유하는 **프롬프트 앞부분(접두부)의 KV Cache를 저장**해 두고, 같은 접두부로 시작하는 다음 요청에서 재사용해 Prefill 계산을 줄이는 서빙 최적화 기법

> KV Cache는 **한 요청 안**에서 이전 토큰을 재사용 — Prefix Caching은 그 재사용 범위를 **요청과 요청 사이**로 넓힌 것

### 접두부(Prefix)란

여러 요청에서 공통으로 반복되는 앞부분:

| 접두부 예시 | 상황 |
|---|---|
| 시스템 프롬프트 | 모든 요청 앞에 붙는 긴 지시문 |
| few-shot 예시 | 매번 동일하게 넣는 예시 |
| 대화 히스토리 | 멀티턴에서 누적되는 이전 대화 |
| 동일 문서 | 같은 문서를 두고 여러 질문 (RAG) |

### 동작 원리 — PagedAttention 블록 재사용

- 접두부를 처음 처리할 때 만든 KV Cache를 저장 → 같은 접두부 요청이 오면 **다시 Prefill하지 않고 재사용**, 달라지는 뒷부분부터 계산
- PagedAttention 블록 중 **공통 접두부 블록**을 요청 사이에서 재사용하는 방식 — vLLM이 접두부 블록에 **해시값**을 부여해 일치 여부 확인, 처음 달라지는 지점부터 새로 계산

> 웹 비유: CDN이 공통 정적 자원을 캐싱하거나 Redis에 자주 조회되는 결과를 저장해 재사용하는 것과 같은 방향

### 사용 이유 — TTFT↓ + 연산 절약

> **TTFT (Time To First Token)**: 요청 후 첫 토큰이 돌아오기까지의 시간 (웹의 TTFB와 유사). 사용자는 전체 응답보다 첫 글자가 뜨는 시점을 먼저 체감 → 스트리밍 UI에서 TTFT가 짧을수록 빠르게 느껴짐

- 공통 접두부를 다시 계산하지 않아 **첫 토큰이 더 빨리** 나옴 (TTFT↓)
- 같은 접두부를 여러 요청이 공유하면 GPU가 반복 계산을 안 해도 됨 → 아낀 연산을 다른 요청에 사용 (동시 처리량↑, 요청당 비용↓)
- **효과는 접두부가 길고 자주 재사용될수록 커짐** — 긴 시스템 프롬프트 챗봇, 고정 few-shot, 같은 문서 기반 RAG에 유리 / 요청마다 앞부분이 다르면 효과 거의 없음

### 사용 방법 — 옵션 활성화 + 접두부 배치

| 순서 | 단계 | 설명 |
|---|---|---|
| 1 | 활성화 | 서버 실행에 `--enable-prefix-caching` 추가 (실습 V0 엔진은 기본 꺼짐) |
| 2 | 공통 접두부 배치 | 시스템 프롬프트·few-shot·문서를 요청마다 **같은 순서·같은 위치**에 배치 |
| 3 | 자동 재사용 | 같은 접두부 요청부터 vLLM이 기존 KV Cache와 비교해 자동 재사용 |

```python
# 공통 접두부(시스템 프롬프트)를 모든 요청에 동일하게 배치
SYSTEM_PROMPT = "당신은 스타트업코드의 친절한 기술 지원 어시스턴트입니다. " * 10

messages=[
    {"role": "system", "content": SYSTEM_PROMPT},   # 공통 접두부 (요청마다 동일)
    {"role": "user",   "content": question},        # 요청마다 달라지는 뒷부분
]
```

> **캐시가 잘 맞으려면 접두부가 요청마다 같은 위치에 있어야 함** — 시스템 프롬프트 앞에 매번 달라지는 시간·사용자별 랜덤 값을 넣으면 접두부가 달라져 재사용 효과↓
>
> V0 엔진 = vLLM 기존 실행 엔진. 최신 V1을 기본 발전시키지만 T4 등 일부 구형 GPU는 V1 미지원 → Colab T4 실습은 `VLLM_USE_V1=0`으로 V0 사용. Prefix Caching은 T4에서 OOM 위험이 있어 A100 환경 권장
